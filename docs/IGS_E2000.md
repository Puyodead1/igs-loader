# IGS E2000: hardware interface and IGS036 protocol

Reversed from Gold Captain (`GoldCaptian-E2000-v1-e65`, executable built
12 Mar 2009).  Disk formats and the boot chain are in
`IGS_ROFS_REVERSE_ENGINEERING.md` (E2000); constants are in `IGS_KEYS.md`.
The loader's implementation is `machines/e2000/` plus the
game plugin `games/goldcaptain/`.

Unlike E2100, the protection is not an FPGA with an ASIC behind
`/dev/pccard0`.  It is an **IGS036**, an ARM-based protection CPU, behind a
**PLX PCI9030** PCI bridge.  The game talks to it through shared RAM.  Go
Go Ball 2 has an **IGS027A** there instead, with a packet transport
(IGS027A transport, below); Speed Rider's, Speed Driver 2's and Panda
Family's IGS036s use transports of their own (IGS036 message and packet
transports, below).

## Devices

| Device | Role | Notes |
| --- | --- | --- |
| `/dev/plx/Pci9030` | PLX SDK driver node | device search (`PlxPciDeviceFind`) |
| `/dev/plx/Pci9030-0` | the card | BAR0 (PLX local registers), BAR2 (message RAM), BAR3 (mailbox) |
| `/dev/plx/Pci9080`, `Pci9054`, `Pci9050`, `Pci9056`, `Pci9656` | other PLX chips | probed; must fail to open |
| `/dev/roio` | BIOS ROM reader | board fingerprint, below |
| `/dev/pccard0` | must open | used only if the BIOS check fails: decoy ioctls, then challenge ioctls `100/110/150/160` → `0xC8/0xD0/0xA8/0xB0 << 24 \| arg` |
| `/dev/dsp`, `/dev/mixer` | OSS audio | through the built-in SDL |

## PLX SDK ioctls (Linux SDK 4.3)

Every request is a 0x24-byte structure with the return code at `+0`
(`512` = success).  A *location* is 18 bytes: bus (u8), slot (u8), device ID
(u16), vendor ID (u16), serial (char[12], e.g. `Pci9030-0`).

| Ioctl | Use | Fields |
| --- | --- | --- |
| `0xC0245104` | find device | `+8` index, or `80001` to count; out: `+8` count, `+12` location |
| `0xC0245100` | location of an open device | out: `+12` location |
| `0xC0245101` | driver version | out: `+8` rev, `+9` minor, `+10` major; the game wants 4.3.0 |
| `0xC0245106` | BAR size | in: `+4` BAR; out: `+8` size |
| `0xC0245105` | BAR properties | in: `+4` BAR; out: `+8` physical address, `+12` I/O flag (must be 0) |
| `0xC024510B` | bind the preceding `mmap(NULL, len, RW, SHARED, fd, 0)` to a BAR | `+4` 1, `+12` address, `+16` physical page, `+20` length |
| `0xC0245103` | (called after mapping) | |

The game maps BAR0, BAR2 and BAR3.

## Shared-RAM transport (`app/c/shareram_operator.c`)

- **BAR2** holds 32-bit words: `[0]` word count, `[1]` message key
  (RC4-encrypted), then the payload, each word XOR the key.  Both
  directions use the same RAM.
- **BAR3** holds eight 16-bit registers.  They read one way and write the
  other, like a mailbox:
  - Read (IGS036 → game): registers 0..7, the game uses each low byte.
    Bytes 0..3 form the status sequence number.
  - Write (game → IGS036): registers 0..6 hold the command sequence
    bytes; register 7 (`+14`) is the doorbell (write 1).
- **Message keys:**
  - Each side picks `rand() % 100000` per message.
  - The key word goes through standard RC4 (OpenSSL's) with a continuous
    stream per direction.
  - RC4 keys are the 9-byte strings, NUL included: `PRIGS036` for IGS036 →
    game and `PR_LINUX` for game → IGS036.

**Exchange** (`sub_80CD1F0`, called every frame and inside waits):
1. If status == `seq`, read the IGS036's message from BAR2.
2. Build the game's message (8 words, or 978 with settings) into BAR2.
3. Write `seq + 1` to the command registers, ring the doorbell, `seq += 2`.
4. The IGS036 answers with its message in BAR2 and status = command + 1.

At start-up the game rings once with command 0 and no message.

| Word | Meaning |
| --- | --- |
| 2 | output bits (lamps, `word_8701440`); Pirate Revenge: the motor (`IOCardMotorValue`) |

The IGS036 therefore holds real game content:
- the game-flow state machine;
- the weapon statistics;
- per-stage parameters (the SOD stage files on disk are loaded, then 30
  values per stage are overwritten from the IGS036).

None of this is in the disk image.  It lives in the IGS036's internal ROM
("36IntRom").  Without a dump, it has to be reconstructed from the game's
use of each value.  Pirate Revenge (`e2000_piraterevenge_m101cn`) uses the
same engine, and its executable (`sship`, stored plainly on p3) keeps its
symbols.  Function and variable names below come from it.  It also takes
the weapon table and WarZones from its IGS036.

### Weapon record (command 15)

Readers: `WeaponDataAssign` (enemy shots), `WeaponDataAssignForPlayer`,
`WeaponProcess`, `CrashWeapon2Role`, `CrashWeapon2Weapon`.

| Word | Field | Use |
| --- | --- | --- |
| 0 | attack | a ship hit loses `attack × (100 − armour) / 100`; types 47..162 grow 10 % per chapter |
| 1 | speed | forward move per frame: animation vector × speed / 10 (`WeaponGetSpeed`) |
| 2 | range | travel left; the shot ends below 0 |
| 3 | reload | frames between shots (`WeaponGetReload`) |
| 4 | life | shots that meet lose each other's life (max 999 after scaling) |
| 5 | | unused |
| 6 | hit width | half-width of the hit cone at its length |
| 7 | hit length | cone length; 0 means an enemy shot never hits |

Types 0..46 are player weapons, 47..162 enemy and boss shots, and 163..167
the pick-up "weapon X" specials.  All-zero records make every shot vanish
on its first frame.

### Wheel calibration

The operator settings (commands 13/14, `SaveData` at `0x86D0060`) hold
the VR calibration in words 958..960.  These are the raw wheel at both
locks and centred, from the test menu (`sub_807BE30`).  The raw value is
`100 − VR / 5.12`.  Factory settings are 0, 0, 0, which pins the
steering (`sub_80CA610` divides by max − min).

## IGS027A transport (Go Go Ball 2)

Go Go Ball 2's protection chip is an IGS027A ("a27", `c/pcicard.c`,
`c/cmdport.c`, `c/protect.c`) behind the same PCI9030, BAR2 and BAR3.
Each request is a synchronous packet exchange.

**Mailbox** (BAR3 byte 0; doorbell: write 1 to BAR3+14).  The game keeps
a sequence number `s` (1..15, wrapping to 1):
1. Start-up (port `0x50`): ring without writing the byte; the chip answers
   `0x80`; `s = 1`.
2. Every packet: `s+1`, wait until the chip's byte has low nibble `s`;
   copy the packet to BAR2; `s+1`, write `s | port`, ring; `s+1`, wait
   (status); `s+1`, write `s | port`, ring.
3. Reply: `s+1`, wait, read BAR2; then `s−1`.

The chip answers each ring with `(s % 15 + 1) | 0x40`; a high nibble of
`0x70` is an assert (text at byte 132), other values are fatal errors.
Ports: `0x20` sprite stores, `0x30` everything else, `0x50` start-up.

**Packet** (32-bit words; the game's buffer is 8324 bytes):

| Word | Meaning |
| --- | --- |
| 0 | nonzero: debug text from byte 8 (chip → game) |
| 1 | `rand() % 256` (game → chip) |
| 16 | reply: data length in bytes; the game reads `len + 132` bytes, at least 232 |
| 17 | sum of words 18..57 (plaintext) |
| 18, 19 | type, function |
| 21.. | parameters; 21 is the data length when there is data |
| 29, 30 | results (`RetVal`, `ErrorVal`) |
| 31 | nonzero: "a27 error", the game exits |
| 33.. | data (byte 132 on) |

Bytes 72..231 are RC4-encrypted, a continuous stream per direction (OpenSSL
RC4).  Keys, 12 bytes: `EncodeGGB` + 3 spaces (game → chip), `DecodeGGB` +
3 spaces (chip → game).  The start-up packet goes in clear; its reply is
encrypted, result 1, error 0.  Type 16 re-keys with 20 bytes of time:
function 0 the chip → game stream (key = words 22..26: mday, hour, min,
sec, ms), function 1 the game → chip stream (words 22..26: ms, sec, min,
hour, mday), each after the packet that carries it.

**Commands** (port `0x30` unless noted):

| Type.function | Meaning | Emulated |
| --- | --- | --- |
| `0x20` 1.0 / 1.1 / 1.2 | ActionGroup store: reset, allocate → result, free word 22 | yes |
| `0x20` 3.0..3.5 | object store: reset, allocate, reserve, in use?, free, free all | yes |
| 3.0/3.1, 3.2/3.3, 4.0/4.1, 5.0/5.1, 6.0/6.1, 7.3/7.4 | settings blocks of 2436, 204, 1044, 32, 40, 48 bytes: load (result 1 = blank, the game writes its defaults) / store | yes, `/rf_data/igs027.nv` |
| 7.6 / 7.9 | light curtain: beam states (word 22 × 2 bytes: 40 x bits, then 24 y bits), beam levels (4 bits each) | all clear |
| 7.0, 7.2, 7.5, 7.7, 7.8, 7.10..7.12, 7.14 | light curtain on/off, tests; 14 → word 22 = UR error | ack |
| 9.0 / 9.1 / 9.6 | ticket dispenser: start one ticket / state in word 30 (1 paying, 2 empty, 3 jam, 6 one out) / done | 0.2 s a ticket |
| 9.4 / 9.5 | tickets owed: get (word 23) / set | yes |
| 10.0..10.7 | ball-stopper motor: go to 0..2, run, stop, 6 → 5 when there, 7 → position (word 22) | 0.5 s per move |
| 11 | coin / ticket meters | ack |
| 12.0 / 12.1 | lamps: set (value, lamp) / read back | yes |
| 13 | every frame: in word 23 the scene; out: word 29 key bits, word 22 blocked cells (2 bytes each from the data: x 0..78, y 0..46), words 23/24 coins on coin 1/2 since the last frame | yes |
| 14 | start-up done | ack |
| 15.0 / 15.1 | password: check words 22..25 → result / set | yes, default 0000 |
| 17.0 / 17.1 | attract: set scene / next scene → result | reconstructed |
| 17.2 / 17.3 | game: set status / event → next status | reconstructed |
| 17.4 | → fault bits (0 = ok) | 0 |
| 18 | 56 bytes: two 28-byte blocks; region (u16 at 8), "I:S" text (20), "O:S" text (48) | dummy texts, `GGB_REGION` |

Key bits (word 29): 1 KEY2, 2 KEY1, 6 test, 7 service, 30 coin switch.

**Light curtain.**  The calibration (settings block 7, factory values at
`0x81E5EE0`) places x beam 19 at pixel `cal[0]` and y beam 11 at `cal[1]`,
`cal[2]` / `cal[3]` tenths of a pixel apart.  The start-up check
(`sub_8067420`) derives the rest; a cell `(x, y)` is then pixel
`cal[0] + cal[2]·(x/2 − 19)/10`, `cal[1] + cal[3]·(y/2 − 11)/10`
(`sub_8065340`).  Each newly blocked cell counts as one ball.

## IGS036 message transport (Speed Rider)

Speed Rider's IGS036 talks through the same BAR2 and BAR3 with a different
layout: header words plus a stream of short sub-messages.  The game runs
one exchange per frame (`sub_80E0490`: receive, update, answer) and loops
on the exchange wherever it waits for the chip.

**Sequence.**  The status byte is BAR3 register 3 (low byte).  The game
reads a message when the status equals its sequence `s`; it answers, writes
`(s+1) | 0x80` to registers 0..6, sets `s = (that+1) | 0x80` and rings
BAR3+14.  The chip answers with status = command + 1 (`| 0x80`).  The chip's
first message is there at power-on; the game reads the status once
(`sub_82D9B20`) and takes it as `s`.

**Message** (BAR2 bytes; the chip's next-message offset at +16 is 0):

| Offset | Content |
| --- | --- |
| +2 | the game writes 1 (16-bit) |
| +8 | message key `K` (RC4) |
| +12 | sub-message bytes `n` (RC4) |
| +16 | offset of the next message (RC4) |
| +20, +24, +28 | lean, throttle, brake as floats (RC4) |
| +32..+60 | 8 button words (XOR `K`): S/Boost, sensor, up, view/down, left, right, test, service |
| +64 | the sequence this message answers (plain; checked after the first) |
| +128 | `n` bytes of sub-messages, XOR `K` |

The game decrypts +8, +16, +20, +24, +28, +12 in that order, then RC4s its
answer's length into +12 and its sub-messages from +128 (XOR the chip's
`K`).  One RC4 stream serves both directions: key `ILoveIGS` (8 bytes);
sub-message 1 re-keys it with an entry of the 9-byte key table
(`IGS_KEYS.md`).

**Sub-messages**: `[length, type, data…, sum | 0x80]`, `sum` the 8-bit sum
of the bytes before it; length 0 ends the list.  Bulk data come 200 bytes
per sub-message.

| Game → chip | Chip → game | Meaning | Emulated |
| --- | --- | --- | --- |
| 1 | 1 `n` | hello; chip: re-key with table entry `n` | entry 0 |
| | 3 | 9 words: ROM and IGS036 versions, fault bits (`sub_832C120` wants 100.0.1 / 109.0.1) | yes |
| 2 `n` | 2 | first 2000 bytes of zip archive `n` | rebuilt (Speed Rider page) |
| `0xC4` `n` / `0xC5` `n` + `0xC6`… | `0x44` | NVRAM block `n` load / store (sizes in `IGS_KEYS.md`) | `/rewrite/igs036.nv` |
| `0xC2` | `0x42` | member-card bit order, 672 words | identity (invented) |
| `0xC3` | `0x43` | member-card key, 8 words, the first byte nonzero | 1, 0… (invented) |
| `0xC0` idx, err, thr | `0x40` idx, thr, brk | AI rider: speed error → throttle, brake | invented law |
| `0xC1` state | `0x41` count, ±index… | UI state → UI elements to show / hide | reconstructed |
| 0x80..0x9D | `0x20` mode | game mode ended (type 0x80 + its class) → next mode | reconstructed |
| 18 n | `0x10` count | coins spent; chip: coin count (credits = count / price) | yes |
| | `0x30` / `0x31` c | button `c` down / up (the game's default event mode) | yes |
| `0x20`..`0x27`, 16, 17, 19, 20 | | lamps, meters, events | ack |
| | `0x11`, `0x12` | coin count from other sources | unused |

**UI** (`UImapping`, `sub_834E030`): for each UI state the game hides
everything, then makes its show/hide calls with a flag that turns them
into no-ops (`sub_83606F0`), sends the state, and the chip sends the
elements.  Index = (UImapping member offset − 84) / 4; `sub_8355550`
applies them.  The plugin's table is those flagged calls.

**Game flow** (`sr::GameFSM`, `sub_80B8C60`): 32 modes (`sub_80B8560`);
each ends by sending its event and sets its next mode to −1, and the FSM
waits until the chip's `0x20` names one.  Events are 0x80 + the class's
alphabetical place (`AddTeam` 0x80 … `CoinSettingMode` 0x9D).

| Mode | # | Event | Next (plugin) |
| --- | --- | --- | --- |
| Idle (attract) | 7 | 0x8B: started, attract page, …, test | test → 19; started → 12; attract page 1/2 → 9; else 7 |
| RankMode | 9 | 0x8F | 7 |
| SelectMode | 12 | 0x92: mode (0 link, 1 story, 2 time attack) | link → 12 again; else 10 |
| SelectCarAndPlayer | 10 | 0x91 | 14 |
| SingleSelect (stage) | 14 | 0x94 | story → 2, time attack → 1 |
| StoryMode / TAMode / RaceMode | 2 / 1 / 0 | 0x96 / 0x97 / 0x8E | 15 |
| Reward | 15 | 0x90 | 18 |
| Continue | 18 | 0x85: 1 = no | no → 9; yes → 14 |
| test and setting modes | | | 19 |

## IGS036 message transport, Speed Driver 2 layout

Speed Driver 2 (`pci/c/pci.cpp`) uses Speed Rider's sequencing (status
byte in BAR3 register 3, `(s+1) | 0x80`, ring BAR3+14), its RC4 key
`ILoveIGS` and its sub-message format, with a header of its own.  The RC4
stream runs chip → game only and is never re-keyed.  One exchange per frame
(`sub_80AEA56`: read, run, write); the loading loops (`sub_80AF202`) also
exchange, every fifth frame, but only the main loop acts on the state.

| Offset | Chip → game | Game → chip |
| --- | --- | --- |
| +2, +8, +12, +34..+46 | | 1, two constants, date and time (16-bit) |
| +20 | message key `K` (RC4) | |
| +24 | sub-message bytes `n` (RC4) | its `n` XOR `K` |
| +28 | counter (plain; `%1000` gates a network check) | |
| +48, +52, +56 | steer (−1 left .. 1 right), gas, brake (0..1), floats (RC4) | |
| +60 | main state (RC4) | the state it moved to, XOR `K`; high word 14 = none |
| +64 | | a request (plain; refit screen: 1), cleared by the chip |
| +68 | frame counter (plain; `%60` paces state 2's network report) | |
| +72 | credits (RC4); a change breaks the attract show | |
| +128 | `n` bytes of sub-messages, XOR `K` | the same |
| +0x3000 | the status this message answers (checked after the first) | |

The game decrypts +20, +48, +52, +56, +60, +72, +24 in that order.

**Main state** (`dword_8BE3A2C`): `main << 16 | sub`; in the result pages the
sub's high byte is the page.  The chip sets it; inside the race and the
replay the game moves on its own and reports each move (+60), and while in
race state ≥ 8.2 it only takes 9, 6, 7 or 2 from the chip.

| Main | What |
| --- | --- |
| 0 | start-up (`PROC_MAIN_INIT`) |
| 2 | title: sub 0 init (runs every frame held), 1 live show (an in-engine race replay, the attract); 3 and 13 draw the ranking (0x8A) |
| 5 | model loading (sub 7 loads, the game sets 5.8) |
| 6 | select screens' 3D background (`vSelectBG`) |
| 8 | race: 0 init, 1 load (blocking), then the game: 3 start, 4 countdown, 5 racing, 6 end (the goal or the player's finish flag), 8 exit |
| 9 | result pages (sub high byte: page; 0 saves the records, 13 the ranking) |
| 11 | operator menu (`vOperator`): 0 init, 2..9 pages with the game's own navigation (2 hardware tests, 3 link, 4 game settings, 5..8 the operator settings menu, 9 data reset), 10 leave |
| 13 | replay, like the race |

**Title step** (game → chip 0x80, every frame in 2.1): 0 init, 1 load, 3
show, 4 fade (credits changed or the show's end), 5 release, 6 over (then
0x40).

attract's ranking pages.
## IGS036 packet transport (Panda Family)

Panda Family's IGS036 (`app/c/shareram.c`) is an I/O board and settings
store; the game logic stays in the executable.  The game maps BAR2 and BAR3
through `libIGS_API.so` (the PLX SDK) and runs one exchange per frame
(`sub_8073420`), looping on it where it waits for an answer.

**Status** (BAR3 registers 0..3, low bytes, as a 32-bit word): sequence
byte | packet length << 8.  When the sequence equals the game's (1 at
start-up), the game reads the packet, answers it in BAR2, writes
`(sequence + 1) | its length << 8` to registers 0..6 and rings BAR3+14; it
then expects sequence + 2.  The chip's first packet must be there at
start-up.  The game resets the board (`PlxPciBoardReset`) before it starts
its RC4 streams.

**Packet** (bytes): `+0` checksum, the 32-bit sum of bytes 4..n−1; from
`+4` sub-messages `[type, length (16-bit), data]`.  Bytes 4..n−1 are XOR
the checksum's low byte, the checksum word goes through RC4 (OpenSSL, a
continuous stream per direction; keys `RC4_36` chip → game, `RC4_PC` game →
chip, 7 bytes with the NUL).  The game asserts on a bad checksum and stops
parsing one byte before the end.

| Game → chip | Chip → game | Meaning | Emulated |
| --- | --- | --- | --- |
| | 2 | key bits (32-bit), every packet | yes |
| 7 / 8 | 3 / 4 | coins on coin 1 / 2 since the last packet; the game acknowledges | yes |
| 5 / 6 | 5 / 6 | I/O board in / out: version words 0, 1 (`I:S%01d%02d`, `O:S…`); in: word 5 bits 0/1 fuse faults | `S100`, no faults (invented) |

| 0x0F | 0x0F | allocate an action group → index (`ActionGroupUse`) | yes |
| 0x10 | 0x10 | free action group (`ActionGroupFree`) | yes |
| 0x11 | 0x11 | load the settings, 3132 bytes; blank is erased (0xFF), the game then writes its defaults | yes, `/PF/pf_data/igs036.nv` |
| 0x12 | 0x12 | store the settings | yes |
